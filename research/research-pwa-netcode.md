# Browser/PWA Gaming on Phones + Real-Time Multiplayer over Mobile Networks — Research Report

## 1. PWA gaming state of the art (2024-2026)
- Successful mobile-browser canon: lightweight session games (Wordle, 2048, .io, portal catalogs). **No famous large-scale RTS shipped primarily as a PWA — the niche is genuinely open.** HTML5 releases nearly tripled YoY: ~15,000 launched H1 2025 (4.9x H1 2023).
- **Install UX**: Android Chrome: `beforeinstallprompt` → programmatic install button, WebAPK. **iOS: NO beforeinstallprompt, no ambient prompt ever** — manual Share → Add to Home Screen; standard practice: detect iOS + !navigator.standalone, show instructional overlay with share-icon graphic. EU: Apple reversed its plan to kill home-screen web apps — they still work, WebKit-only.
- **iOS storage/eviction (the big one)**: since iOS 13.4, all script-writable storage for a site not visited in 7 days is DELETED — **home-screen-installed web apps are exempt**. ~50MB Cache API ceiling historically; Safari 17 raised quota + added Persistent Storage API (persistence tied to notification permission on Safari). Clearing Safari history nukes PWA caches. **Principle: a self-contained HTML file well under 50MB, SW-cached, installed to home screen = most eviction-resistant config on iOS. Treat client storage as cache, not database; mirror saves server-side or offer export.**
- iOS PWA gaps: no Background Sync/Fetch; push only for installed PWAs 16.4+; no true fullscreen (status bar persists; Fullscreen API iPhone = video only); no orientation lock; 100vh bug (use dvh/-webkit-fill-available); no Web Bluetooth/USB.
- **SW update strategy for games**: anti-pattern = blind skipWaiting() — mid-session takeover serves mixed versions and for lockstep silently swaps sim code mid-match (guaranteed desync on version skew). Best practice: new SW waits; show "Update available" OUTSIDE matches only; user-driven SKIP_WAITING + controllerchange reload. **Corollary: include build hash in room handshake and refuse cross-version matches — SW timing makes version skew routine.** iOS updates SW lazily; users run stale builds for days — version check over the WebSocket at match start is the reliable gate.

## 2. Mobile browser performance & quirks
- **iOS Safari WebGL**: WebGL2 since Safari 15 (ANGLE-over-Metal). History of severe regressions (15.2 perf disaster; iOS 18.4 broke Unity WebGL on some iPads). `gl.getParameter` unusually expensive on Safari — cache all parameter queries. **Every iOS point release is a potential regression — keep a rendering-path toggle/fallback.**
- **iOS memory**: page budget ~300-450MB before Jetsam force-reloads; canvas memory capped (~384MB iOS 15); Safari hoards detached canvases (resize-to-1x1-and-clear to release); iOS 17.x canvas-resize leak. Anti-pattern: many large offscreen canvases for atlases on iOS.
- **Background throttling (exact)**: rAF STOPS entirely in hidden tabs (all browsers) — never drive sim from rAF alone. Chrome: hidden = timers 1x/second; hidden >5 min (+conditions) = intensive throttling 1x/minute; **active WebRTC exempts; WebSocket alone does NOT**; playing audio exempts. **iOS Safari far harsher: JS suspended within ~7-8s of backgrounding; WebSockets killed.** Page Visibility API fires before suspension. **Principle: on `hidden`, immediately send the server a "going dark" courtesy packet.** Workers don't help on iOS (whole page suspended).
- **Wake Lock**: navigator.wakeLock in all browsers now; Safari since 16.4 but **broken inside installed home-screen web apps until iOS 18.4 (fixed 2025-03-31)**. Auto-released on visibility loss — re-request on visible. **Essential for RTS: users watch battles without touching → screen dims → iOS kills the socket.**
- **Audio unlock**: AudioContext suspended until resume() inside a user gesture; iOS: unlock on **touchend/pointerup** (touchstart may not qualify). iOS 17 regression: audio dies after interruptions — re-resume on visibilitychange; handle statechange→'interrupted'. "Tap to start" gate doubles as audio unlock + wake-lock request.
- **Input**: Pointer Events + `touch-action: none` on canvas; suppress double-tap zoom, user-select, -webkit-touch-callout; **guard iOS left-edge swipe = history back (match-killer; standalone PWA mode removes URL bar and reduces hazard — another argument for install)**.
- Viewport: viewport-fit=cover + env(safe-area-inset-*); 100dvh; visualViewport for keyboard overlap.
- **120Hz**: Safari caps rAF at 60Hz even on ProMotion (user flag needed — don't rely); Chrome Android delivers 90/120Hz rAF. Never assume 60; decouple sim from render.
- **Thermal**: flagships sustain peak GPU ~2-5 min; budget phones step down in 60-90s; sustained FPS drop mid-match looks like lag. Frame-cap (30fps option), reduced-effects mode; in lockstep a thermally-throttled client that can't hit tick rate slows everyone — adaptive turn length keyed to slowest machine matters as much as ping.

## 3. Lockstep RTS networking
- **Canonical numbers**: AoE "1500 Archers": 200ms communication turns, 2-turn scheduling; turn length adjusted from pings + slowest machine, changed "a few ms per turn"; **≤250ms command latency unnoticed, 250-500ms very playable, >500ms noticeable**. StarCraft: ~219ms average turns. SupCom: 10 tps sim, 60fps interpolated render, 200-300ms command latency masked by instant UI/audio acknowledgment; state hashed 1x/sec, mismatch = fatal. Factorio: 60 UPS, client-server input relay; latency-state (local speculative over authoritative); server renegotiates each client's latency allowance every 5s; missed input window → server proceeds without it, action retries next tick (delayed never dropped, one laggy client doesn't stall the server). Megapacket lesson: cap and coalesce queued commands after reconnect.
- **Gaffer On Games**: playout-delay buffer +100ms baseline for jitter; catch-up cap ~4 sim frames per render frame; **TCP is the failure mode** — 100ms RTT + 1% loss = visible hitches; 250ms + 5% unplayable; UDP with redundant input resend survives 2s + 25% loss. **Browser reality: WebSocket = TCP head-of-line blocking; mitigations: large-enough command delay, adaptive delay, tolerate-and-catch-up (run stalled ticks fast when the burst arrives). WebRTC DataChannel (unreliable) is the only UDP-like path — also buys Chrome's intensive-throttling exemption.**
- **Adaptive delay**: input delay ≈ ½ median RTT + jitter margin; adapt slowly up on late inputs, decay slowly down. On cellular, **design for p95 (≈150-300ms), not mean**; occasional 1-3s outliers (handover, RRC) handled by stall UX + catch-up, not delay inflation.
- **Multi-second stalls**: (1) "Waiting for player X" overlay after ~1-2s; (2) server keeps ticking, stalled client fast-forwards (Factorio — better for >2 players); (3) bound fast-forward: >N seconds behind = disconnect → rejoin flow.
- **Reconnect**: Factorio = state snapshot from server + replay buffered inputs. Relay-only options: (a) designated peer uploads snapshot through relay; (b) relay records full command log, rejoiner re-simulates from start (cheap for server, cost grows with match length); (c) hybrid periodic compressed checkpoints.
- **Rollback vs lockstep**: rollback needs full-state serialization + re-sim per correction — prohibitive with hundreds of units on phones; RTS latency tolerance removes rollback's benefit. **Lockstep with command delay + local acknowledgment remains correct for RTS.**
- **Desync detection**: tiered hashing (every tick a small vital tuple: unit count, total HP, resources, RNG state; full hash rarely). **Hash input stream SEPARATELY from state: input hashes diverge → network bug; inputs match but state diverges → sim nondeterminism. The single most valuable debug practice.** Recovery ≈ none: end match with error or drop-and-rejoin-from-snapshot. Ship desync forensics: both clients upload state dump + command log on mismatch.
- **Mobile network characteristics**: 4G LTE typical RTT 30-50ms good, spikes 100ms+; 5G NSA often no better than LTE; Wi-Fi ~12ms avg with interference spikes ~150ms. **Means are fine, tails are the problem.**

## 4. Mobile-specific multiplayer failure modes
- **iOS backgrounding kills everything**: screen lock/app-switch → JS suspended in seconds, WebSocket unusable — and the JS object still LOOKS open but send() silently does nothing (**zombie socket**). Android: rAF stops, timers throttle, socket usually survives minutes but Doze can kill.
- **Handling pattern**: on visibilitychange→hidden send "backgrounded" notice; on →visible **assume socket dead — proactively close and reconnect with session token, don't wait for timeout**; server holds seat through grace period (30-120s typical). Lockstep elegance: a reconnecting player can catch up purely from the buffered command log.
- **Radio state transitions**: LTE RRC IDLE→CONNECTED promotion costs hundreds of ms up to >1s; phones demote radio after ~10-20s idle. **A 20 tps tick stream prevents demotion (consistent latency at battery cost); killer spikes come at match start after lobby idle. Anti-pattern: letting the connection go quiet in menus, then wondering why the first command takes 1.5s.**
- **Carrier NAT**: CGNAT idle timeouts ~28-30s — silent mapping drop, blackholed packets. In-match traffic keeps mappings alive; **lobby/menu states need app-level heartbeat ≤20-25s.**
- **Battery**: radios #2 consumer after screen; a network event every ~15s keeps cellular radio pinned. In-match moot (radio pinned anyway; expect video-call-level battery); optimize lobbies/post-match: slow heartbeat or close socket on long idle with fast resume.

## 5. WebSocket relay architecture (indie scale)
- **Heartbeats**: browser JS can't see protocol ping/pong — app-level heartbeats mandatory client-side. Rule: interval = 75% of shortest intermediary timeout. Known timeouts: Heroku 55s, nginx 60s, AWS ALB 60s, HAProxy 50-60s, Cloudflare ~100s, Google Cloud LB 30s, **mobile CGNAT ~28-30s**. **Practical mobile answer: 15-25s app-level heartbeat**, 10s pong timeout, dead after 2-3 missed. In-match the tick stream IS the heartbeat.
- Reconnect: exponential backoff with jitter (1s→30s cap), session-token resume, **immediate attempt on visibilitychange→visible (skip backoff)**.
- **Render free tier**: spin-down after 15 min no traffic (WS messages count as traffic — active heartbeat prevents spin-down); spin-up ~1 min; 750 free instance-hours/month. Mitigations: warm the server when the player opens the lobby page (fetch on page load, before "create room"); honest "waking server (~60s)" UX.
- **Room codes**: 4 letters A-Z case-insensitive is the party-game standard (Jackbox; 456,976 combos); filter profanity-adjacent; exclude ambiguous chars if mixing digits; expire empty rooms in minutes; **support join-by-URL (?room=XXXX) — mobile users share via messaging apps, deep link straight into lobby**. Open-room enumeration is real — "start locked until host confirms" if griefing matters.

## 6. Determinism in JavaScript across devices
- Best primary source: Rune "Making JS deterministic for fun and glory" (ships deterministic lockstep JS games across Android/iOS at scale).
- **Basic IEEE754 arithmetic (+ - * /, Math.sqrt, Math.fround) is spec-pinned — bit-identical across V8/JSC in principle** (caveat: JIT must not use FMA/x87 — modern ARM64/x64 don't; ship a runtime self-test anyway).
- **Math.sin/cos/tan/exp/log/pow/atan2 are implementation-approximated per spec — V8 vs JSC DIFFER. Any transcendental in the sim path is a desync bug on iOS-vs-Android.**
- Mitigations by robustness: (1) integer/fixed-point sim math (exact up to 2^53; Math.imul/bitwise exact 32-bit); (2) own deterministic sin/cos via LUT or polynomial from pinned ops; (3) round Math results through Math.fround (pragmatic, not bulletproof).
- Other desync sources: Math.random (seeded PRNG, serialize state); **Array.prototype.sort — stable since ES2019 but comparator ties are a trap: always sort with a total deterministic key (unit ID tiebreak)**; Map/object iteration = insertion order (only deterministic if insertion order is); Date.now/performance.now in sim; locale functions.
- **Practices: startup determinism self-test (hash a few thousand mixed ops vs golden hash — mismatch → warn/refuse multiplayer); CI cross-platform replay tests (Factorio pattern); dual hashing (inputs vs state).**

## 7. Distribution & discovery
- Portals dwarf self-hosting: Poki ~100M MAU 2026 (10M in 2020); CrazyGames 50M+ players. Case: one browser game hit 42M sessions in Q3-Q4 2025 via Poki algorithmic promotion. Revenue: $200-2,000/month typical rev-share; top of catalog ~€1M/yr.
- Portal constraints: CrazyGames total ≤250MB, initial ≤50MB, ≤20MB for mobile-homepage eligibility, ≤1500 files — a single self-contained HTML sails through. Multiplayer games must integrate SDK room-data; portals drop MP games whose empty lobbies feel dead → **bot/AI fallback is the standard hedge**. Poki requires its SDK; pushes Netlib (WebRTC P2P).
- What drives traffic: portal algorithms (session thresholds trigger promotion), thumbnail/first-30s retention, Discord/Reddit WoM, itch.io jams. Self-hosted discovery ≈ zero without funnels; standard play: portal for discovery + own domain for installed-PWA community version.
- **App-store wrapping**: Apple hostile (Guideline 4.7; "by 2026 wrapping a web app is almost a guarantee of rejection"). Android TWA viable but marginal. **Ranking: portal (discovery) + self-hosted PWA (retention) >> TWA (optional) >> iOS wrapper (don't).**

## Cross-cutting principles
1. 250ms/5-tick delay is canonically correct — make it adaptive upward under measured jitter, a few ms per turn, never jumps.
2. WebSocket = TCP head-of-line blocking; compensate with stall-tolerant bounded fast-forward, not bigger static delay.
3. Treat every return-to-foreground as a dead socket on iOS; proactive reconnect with session token; server holds seats 30-120s.
4. Keep the wire warm: heartbeat ≤25s always; warm the server on lobby-page load; traffic during menus avoids RRC spikes at match start.
5. Determinism: no Math.random/transcendentals in sim, deterministic sort keys, seeded PRNG, startup self-test, dual hashing, desync = end match + forensic dump.
6. iOS survival kit: home-screen install (escapes 7-day eviction + edge-swipe); tap-to-start gate (audio unlock on touchend + wake lock); re-acquire wake lock + re-resume audio on every visibilitychange; stay under ~300MB; rendering-path fallback; iOS ≥18.4 for wake lock in installed PWAs.
7. SW updates: never skipWaiting mid-match; version-gate rooms at handshake; assume week-stale clients on iOS.
8. Distribution: single-file <20MB build is portal-ready; MP-only games die on portals without bots/AI fallback; skip iOS app-store wrapping.
